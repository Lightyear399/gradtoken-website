Mission 04 — Put It On-Chain

Lesson 4: Testing, Deploying & Verifying on Sepolia

Dependency: Lessons 1–3, and a working Mission 02 or Mission 03 contract.

  • write automated tests covering success paths and failure paths
  • explain what deployment, testnets and verification actually are
  • deploy a contract to Sepolia from Remix with MetaMask
  • verify it on Etherscan and interact with it there
  • diagnose the common reasons verification fails
THEORY

4.1 THEORY — Why Test, and What "Deploy" and "Verify" Mean

Testing: once deployed, your contract's code can't be edited. A bug is permanent, and it may hold other people's money. Tests are how you find bugs while they're still free to fix. Clicking buttons in Remix (what you've done so far) is manual testing; this mission adds automated tests that re-check everything in seconds whenever you change code.

A testnet is a public blockchain that works like Ethereum mainnet but uses ETH with no real value. Sepolia is Ethereum's main testnet for application developers. Test ETH comes free from faucets.

Deploying means sending a special transaction with no recipient, whose data is your compiled bytecode (plus any constructor arguments). The network runs the constructor, stores the resulting code, and assigns the contract a permanent address.

Verifying means publishing your source code and compiler settings to a block explorer like Etherscan. Etherscan compiles your source with the exact same settings and checks the output matches the bytecode on-chain. If it matches, it shows your source publicly with a "verified" mark and adds Read/Write buttons. Anyone can now check that the code does what you claim.

ANALOGY

4.2 ANALOGY — Opening a Restaurant

  • Testing = the kitchen rehearsal before opening night. You deliberately try the awkward orders — a customer who can't pay, an order for a dish you don't have — not just the easy ones.
  • Deploying = opening the doors. The restaurant now has a public address, and the building can't be remodeled.
  • Verifying = publishing the full recipe book, with an inspector who cooks every dish from your recipes and certifies it tastes identical to what you serve. Customers don't have to trust you — they can check.
  • Sepolia = a practice restaurant where diners pay with play money.
THEORY

4.3 THEORY — What to Test — PART A: TEST

For every function, test:

CategoryQuestionExample (SecureVault)
Happy pathDoes it work when used correctly?Owner sets value to 42 → value is 42
Access controlAre unauthorized callers rejected?Non-owner sets value → reverts "Not owner"
Input validationAre bad inputs rejected?Deposit of 0 → reverts
Edge casesWhat about boundaries?Withdraw exactly the full balance; withdraw 1 wei more
State after failureIs state unchanged after a revert?Failed withdraw leaves balance as it was
Value movementDid ETH actually move?Withdrawer's ETH balance increases by the amount
Rule: every require, revert and modifier in your contract should have at least one test that makes it fail on purpose. Failure paths are where security bugs hide.
EXAMPLE

4.4 EXAMPLE — Automated Tests with the Remix Unit Testing Plugin

Remix has a built-in test runner. Tests are written in Solidity.

Setup:

  1. In Remix, open Plugin Manager and activate Solidity Unit Testing (the flask icon).
  2. Put your contract at contracts/SecureVault.sol (the SecureVault from 2.8).
  3. Create contracts/NotOwner.sol (helper, below).
  4. Create tests/SecureVault_test.sol. Test files must end in _test.sol.

How the runner works:

  • Every public function in the test contract is a test, except special hooks such as beforeEach (runs before every test) and beforeAll (runs once at the start).
  • Assert.equal(actual, expected, message) and Assert.ok(condition, message) report pass/fail.
  • A comment /// #value: <wei> above a payable test function sends that much ETH with the test call.
Important: when the test contract deploys SecureVault with new, the test contract is msg.sender, so the test contract becomes the owner. To test a non-owner, you need a second contract to make the call — that's the job of the helper.

Helper — contracts/NotOwner.sol:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "./SecureVault.sol";

// Plays the role of "Bob": a caller who is not the owner.
contract NotOwner {
  function trySetValue(SecureVault vault, uint256 newValue) external {
    vault.setValue(newValue);
  }
}

Test file — tests/SecureVault_test.sol:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "remix_tests.sol";
import "../contracts/SecureVault.sol";
import "../contracts/NotOwner.sol";

contract SecureVaultTest {
  SecureVault vault;
  NotOwner stranger;

  // Fresh contracts before every test, so tests don't affect each other
  function beforeEach() public {
    vault = new SecureVault();
    stranger = new NotOwner();
  }

  // ---------- Access control ----------
  function deployerIsOwner() public {
    Assert.equal(vault.owner(), address(this), "Deployer should be owner");
  }

  function ownerCanSetValue() public {
    vault.setValue(42);
    Assert.equal(vault.value(), uint256(42), "Value should be 42");
  }

  function nonOwnerCannotSetValue() public {
    try stranger.trySetValue(vault, 99) {
      Assert.ok(false, "Non-owner call should have reverted");
    } catch Error(string memory reason) {
      Assert.equal(reason, "Not owner", "Wrong revert reason");
    } catch {
      Assert.ok(false, "Reverted for an unexpected reason");
    }
    Assert.equal(vault.value(), uint256(0), "Value must be unchanged");
  }

  // ---------- Deposits ----------
  /// #value: 1000000000000000000
  function depositRecordsBalance() public payable {
    vault.deposit{value: msg.value}();
    Assert.equal(vault.balances(address(this)), msg.value, "Balance not recorded");
  }

  function zeroDepositReverts() public {
    try vault.deposit{value: 0}() {
      Assert.ok(false, "Zero deposit should revert");
    } catch Error(string memory reason) {
      Assert.equal(reason, "Must deposit ETH", "Wrong revert reason");
    }
  }

  // ---------- Withdrawals ----------
  /// #value: 1000000000000000000
  function withdrawReturnsEth() public payable {
    vault.deposit{value: msg.value}();
    uint256 before = address(this).balance;
    vault.withdraw(msg.value);
    Assert.equal(vault.balances(address(this)), uint256(0), "Balance should be 0");
    Assert.equal(address(this).balance, before + msg.value, "ETH not received");
  }

  /// #value: 1000000000000000000
  function overWithdrawReverts() public payable {
    vault.deposit{value: msg.value}();
    try vault.withdraw(msg.value + 1) {
      Assert.ok(false, "Over-withdraw should revert");
    } catch Error(string memory reason) {
      Assert.equal(reason, "Insufficient balance", "Wrong revert reason");
    }
    Assert.equal(vault.balances(address(this)), msg.value, "Balance must be unchanged");
  }

  // The vault sends ETH back to this contract during withdraw,
  // so the test contract must be able to receive it.
  receive() external payable {}
}

How the failure tests work — try / catch:

  • try someContract.f() { ... } — the first block runs only if the call succeeded. In a failure test, that means the test should fail, so we call Assert.ok(false, ...).
  • catch Error(string memory reason) { ... } — runs if the call reverted with a require message. We check it's the expected message, so the test doesn't pass by accident when the call fails for a different reason.
  • try/catch only works on calls to other contracts — another reason the helper contract exists.

Run it: open the Solidity Unit Testing tab, select the test file, click Run. Every test should show a green tick.

Testing custom errors — if a function reverts with a custom error instead of a string, catch the raw error data and compare its first 4 bytes (the error's selector):

try registry.updateScore(someone, 90) {
  Assert.ok(false, "Should revert");
} catch (bytes memory data) {
  Assert.ok(bytes4(data) == StudentRegistry.Unauthorized.selector, "Wrong error");
}
Beyond the course: Foundry (optional). This box is additional material, not required for GradLearn. Professional teams often test with Foundry, a command-line toolkit where tests are also written in Solidity but use "cheatcodes" to control the test environment. vm.prank removes the need for helper contracts. If you continue past this course, Foundry is a strong next step.
INTERACTIVE

4.5 INTERACTIVE — Will This Test Catch the Bug?

A teammate "optimizes" SecureVault's withdraw and accidentally deletes the require(balances[msg.sender] >= amount, ...) line. Look at the test suite in 4.4.

  1. Which test fails?
  2. Why doesn't the contract just let the over-withdraw through? (Hint: Lesson 1, checked arithmetic.)
  3. Does the test still pass, fail, or fail for the "wrong reason"?
Reveal

1. overWithdrawReverts. 2. balances[msg.sender] -= amount would go below zero, so 0.8's checked arithmetic reverts — but with a Panic error, not "Insufficient balance". 3. The call still reverts, but not with an Error(string), so neither the success block nor the catch Error block runs. Since that try has no fallback catch, the revert propagates and the test fails. That's why it's worth checking the reason: the contract is still "safe" by accident, but users would get a confusing error, and the test flags that the intended check is gone.

PRACTICE

4.6 PRACTICE — Test Your Own Contract

Write a test file for your Mission 03 registry (or your Mission 02 vault). Minimum:

  • one happy-path test per state-changing function
  • one failure test per require, revert and modifier
  • at least one test that checks state is unchanged after a failed call

Every test should have a name that says what it checks, like nonOwnerCannotUpdateScore, not test3.

Remix's test runner doesn't check events directly. Check your events manually in the Remix terminal logs and screenshot them. (In Foundry, vm.expectEmit does this automatically.)
THEORY + PRACTICE

4.7 THEORY + PRACTICE — Deploy to Sepolia — PART B: DEPLOY

Safety first:

  • Use a separate development wallet that has never held real funds.
  • Never share, paste or commit your seed phrase or private key — not to Remix, not to an AI tutor, not to GitHub. No legitimate step in this course needs it.
  • Sepolia ETH has no value. Anyone offering to sell it to you is running a scam.

Steps:

  1. Get test ETH. In MetaMask, switch to the Sepolia network (enable "show test networks" in settings if you can't see it). Get Sepolia ETH from a faucet. A small amount (around 0.05 Sepolia ETH) is plenty for this course.
  2. Compile your contract in Remix with 0.8.24. Note two settings on the compiler tab — you'll need them for verification: optimization on/off (and runs, if on), and the EVM version under Advanced Configurations (leave it on default and simply note it).
  3. Connect. In Deploy & Run, set Environment to Injected Provider – MetaMask. Approve the connection. Check that Remix shows the Sepolia network and your dev account.
  4. Constructor arguments: if your constructor takes parameters, fill them in next to Deploy and write down exactly what you entered.
  5. Deploy. Click Deploy and confirm in MetaMask. Wait for confirmation (usually a few seconds).
  6. Record your evidence in a notes file: contract address, deployment transaction hash, compiler version, optimization setting, EVM version, constructor arguments, if any.
  7. Interact. Make at least one write call (costs Sepolia gas, needs MetaMask confirmation) and one read call. Record the write transaction's hash.
  8. Open https://sepolia.etherscan.io/address/<your address> and find your deployment and write transactions.

PRACTICE

4.8 PRACTICE — Verify on Etherscan — PART C: VERIFY

Option 1 — Etherscan website ("Verify and Publish"):

  1. Open your contract address on Sepolia Etherscan → Contract tab → Verify and Publish.
  2. Compiler type: Solidity (Single file). Compiler version: the exact version you compiled with — the entry starting v0.8.24+commit…. License: MIT (match your SPDX line).
  3. Paste your full source code, exactly as compiled.
  4. Under advanced settings, set optimization and EVM version to match what Remix used.
  5. If your constructor had arguments, Etherscan usually detects them from the deployment transaction. If asked, supply them ABI-encoded (Option 2 does this for you).
  6. Submit. On success, the Contract tab shows a green tick and your source code.

Option 2 — Remix verification plugin:

Activate Remix's Contract Verification plugin in the Plugin Manager. It reads your compiler settings from Remix and encodes constructor arguments for you. Etherscan verification through a plugin needs a free Etherscan API key from your Etherscan account — treat it like a password and don't share it or commit it.

If your contract imports other files, single-file verification fails unless you flatten the source (Remix: right-click the file → Flatten) or use the plugin, which handles imports.

After verifying: open the Read Contract and Write Contract tabs on Etherscan. Connect MetaMask on the Write tab and make one more write call from Etherscan itself. This proves anyone can interact with your verified contract without Remix.

DEBUG

4.9 DEBUG — Deployment Edition

Problem 1: "Bytecode mismatch" / "Unable to verify". Work through these in order and fix one thing at a time:

  1. Compiler version. Must match the version Remix actually used, not just the pragma. ^0.8.24 allows 0.8.25, 0.8.26…, so if Remix auto-selected a newer version, select that one on Etherscan (or recompile with 0.8.24 and redeploy).
  2. Optimization. On/off and the runs number must match exactly.
  3. EVM version. Must match the Remix setting. Different compiler versions have different defaults, so check what Remix used rather than guessing.
  4. Source code. Must be exactly what you compiled. Even adding a comment after deploying can cause a mismatch, because the compiler embeds a fingerprint of the source in the bytecode.
  5. Constructor arguments. Must be the exact values used at deployment, correctly ABI-encoded.
  6. Imports. Single-file verification needs a flattened file.

Problem 2: Diagnose the student. A student reports: "Remix says my contract compiled with 0.8.26+commit…. On Etherscan I picked v0.8.24 because that's what my pragma says. Verification fails."

Reveal

The pragma ^0.8.24 allowed 0.8.26, and Remix used it. Etherscan must use the version that actually compiled the deployed bytecode. Fix: (1) select v0.8.26… on Etherscan, or (2) recompile with exactly 0.8.24 in Remix, redeploy, and verify with 0.8.24. Option 2 matches course policy.

Problem 3: "Transaction failed" when deploying. Common causes: not enough Sepolia ETH for gas, MetaMask on the wrong network, or the constructor itself reverting (for example, a require in the constructor failing on the arguments you entered). Read the MetaMask error and the Remix terminal message first before guessing.

CHECK

4.10 CHECK — Knowledge Check

  1. What does verification actually prove?
  2. Why deploy to Sepolia instead of mainnet while learning?
  3. Your pragma is ^0.8.24. Is that enough information to verify?
  4. What's the difference between a contract address and a transaction hash?
  5. Why should every require in your contract have a failing test?
Reveal

1. That the published source code, compiled with the stated settings, produces exactly the bytecode running at that address. It proves what the code is — not that the code is bug-free or safe. 2. Sepolia ETH has no value, so mistakes cost nothing, while everything else works like the real network. 3. No. You need the exact compiler version used, plus optimization and EVM version settings. 4. The address identifies the contract (where it lives). The transaction hash identifies one transaction (for example, the one that deployed it). 5. Because a check that's never tested failing might not work — or might fail for the wrong reason — and failure paths are where security bugs hide.

MINI TEST

4.11 MINI TEST — Lesson 4 (pass: 4/5)

Q1. In the Remix test runner, beforeEach deploys vault = new SecureVault();. Who is the vault's owner?
Q2. Why does SecureVaultTest need a receive() function?
Q3. A test does this. What's the weakness? try vault.withdraw(5 ether) { Assert.ok(false, "Should revert"); } catch { Assert.ok(true, "Reverted"); }
Q4. You deployed, then added a comment to your source "to explain it better," then tried to verify. It fails. Why?
Q5. Name three settings that must match between Remix and Etherscan for verification to succeed.
Reveal answers

1. The test contract — it's msg.sender when new SecureVault() runs. 2. withdraw sends ETH to msg.sender, which is the test contract. Without receive(), the transfer fails and the withdraw reverts with "ETH transfer failed". 3. It accepts any revert, so it would pass even if the call failed for the wrong reason (a bug, a panic, a different require). Catch Error(string memory reason) and check the reason (or check the custom error selector). 4. The compiler embeds a fingerprint of the exact source in the bytecode. Changed source means different bytecode. Verify the exact source you deployed. 5. Any three of: compiler version, optimization on/off and runs, EVM version, (plus exact source code and constructor arguments).
