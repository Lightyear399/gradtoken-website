Mission 03 — Build the Student Registry

Lesson 3: Mappings, Structs, Events & Data Locations

Dependency: Lessons 1–2: variables, functions, msg.sender, modifiers, constructors.

  • store data per address with mappings, and explain their default-value behavior
  • group related data with structs
  • choose correctly between storage, memory and calldata
  • validate string input
  • emit events and read them in Remix and Etherscan
THEORY

3.1 THEORY — Mappings

mapping(address => uint256) public scores;

Simply: a key → value lookup table. Give it an address, get a number.

Technically:

  • Every possible key already "exists" and returns the default value until set: 0, false, address(0), "".
  • A mapping has no length and cannot be looped over. It doesn't know which keys have been set.
  • Mappings can only live in storage.
  • A public mapping gets a getter that takes the key as input: scores(someAddress).
Consequence: because an unset key returns defaults, you can't tell "never registered" from "registered with a score of 0" unless you store something that shows registration — like an enrolled flag.
THEORY

3.2 THEORY — Structs

A struct groups related fields into one custom type:

struct Student {
  string name;
  uint256 score;
  bool enrolled;
}

mapping(address => Student) public students;

Two ways to create one:

Student(name, 0, true) // by position
Student({name: name, score: 0, enrolled: true}) // by name — clearer, safer

The named form is safer: if someone reorders the struct fields later, positional code silently puts values in the wrong fields.

ANALOGY

3.3 ANALOGY — The School Registrar's Office

  • The struct is the blank enrollment form: every student's form has the same fields (name, score, enrolled).
  • The mapping is a filing cabinet with one drawer per wallet address. Every drawer exists, but most are empty — opening an empty drawer gives you a blank form (default values), not an error. There's no index of which drawers are full.
  • An event is the public announcement board outside the office. When someone enrolls, a notice goes up: "0xAbc… enrolled as Ada." Anyone passing by (apps, Etherscan) can read the board, but the clerks inside (the contract) can't look back at old notices.
  • storage vs memory: editing the form in the drawer (storage) versus photocopying it and scribbling on the copy (memory) — the copy's changes never reach the drawer.
  • calldata is the sealed envelope the student hands in. You can read it and file its contents, but you can't write on it.
THEORY

3.4 THEORY — Data Locations: storage, memory, calldata

LocationWhereMutable?LifetimeTypical use
storageContract's permanent stateyespermanentstate variables; local references to state
memoryTemporary workspaceyesone callbuilding or returning temporary values
calldataThe call's input datano, read-onlyone callfunction parameters you only read

Key points:

  • calldata is not memory. It's a separate, read-only area holding the input data of the call. Using it for parameters you don't modify avoids copying the data into memory, which saves gas.
  • You must write the location for reference types (string, bytes, arrays, structs) in function parameters, return values and local variables. Value types (uint256, bool, address) don't take a location.
  • Student storage s = students[a]; creates a reference — changes to s change the stored data.
  • Student memory s = students[a]; creates a copy — changes to s are lost when the function ends.

INTERACTIVE — Copy or reference?

function bumpCopy() external {
  Student memory s = students[msg.sender];
  s.score = 100;
}

function bumpRef() external {
  Student storage s = students[msg.sender];
  s.score = 100;
}

Your stored score starts at 0. Predict your stored score after each:

Reveal
CallStored score after
bumpCopy()0 — only the temporary copy changed
bumpRef()100 — the reference points at storage

bumpCopy is a classic silent bug: it compiles, runs, costs gas, and does nothing useful. (The compiler may even warn you that s is never used after being changed.)

THEORY

3.5 THEORY — Validating Strings

You can't compare strings with == or != in Solidity. To check a string isn't empty, convert it to bytes and check its length:

require(bytes(name).length > 0, "Name cannot be empty");
require(bytes(name).length <= 32, "Name too long");
bytes(name).length counts bytes, not characters. Plain English letters are 1 byte each, but many other characters (accents, emoji, non-Latin scripts) take 2–4 bytes. A limit like 32 bytes is a storage-cost and abuse guard, not an exact character count.
THEORY

3.6 THEORY — Events

event StudentRegistered(address indexed student, string name);

emit StudentRegistered(msg.sender, name);
  • Events write to the transaction's logs, not to contract storage. Logs are cheap and readable by off-chain apps and explorers.
  • Contracts cannot read events — not even their own.
  • If the transaction reverts, its events disappear too.
  • indexed makes a parameter filterable ("show me all registrations for address X"). An event can have up to 3 indexed parameters.
  • Indexing a string stores only its hash, not the readable text. That's why name above is not indexed.

Emit an event for every important state change. It's how the outside world follows your contract.

EXAMPLE

3.7 EXAMPLE — StudentRegistry

This version fixes two weaknesses from the earlier draft: students can't re-register to wipe their score, and only the owner can update scores.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract StudentRegistry {
  struct Student {
    string name;
    uint256 score;
    bool enrolled;
  }

  address public owner;
  mapping(address => Student) public students;

  event StudentRegistered(address indexed student, string name);
  event ScoreUpdated(address indexed student, uint256 oldScore, uint256 newScore);

  error Unauthorized(address caller);

  modifier onlyOwner() {
    if (msg.sender != owner) revert Unauthorized(msg.sender);
    _;
  }

  constructor() {
    owner = msg.sender;
  }

  // calldata: we only read `name`, never modify it
  function register(string calldata name) external {
    require(bytes(name).length > 0, "Name cannot be empty");
    require(bytes(name).length <= 32, "Name too long");
    require(!students[msg.sender].enrolled, "Already registered");
    students[msg.sender] = Student({name: name, score: 0, enrolled: true});
    emit StudentRegistered(msg.sender, name);
  }

  function updateScore(address studentAddr, uint256 newScore) external onlyOwner {
    Student storage student = students[studentAddr];
    require(student.enrolled, "Not enrolled");
    uint256 oldScore = student.score;
    student.score = newScore;
    emit ScoreUpdated(studentAddr, oldScore, newScore);
  }

  function isEnrolled(address studentAddr) external view returns (bool) {
    return students[studentAddr].enrolled;
  }
}

Read it before running it:

  1. Why does register use msg.sender as the key instead of taking an address parameter?
  2. Why does updateScore use storage and not memory?
  3. What would go wrong without the "Already registered" check?
Reveal

1. So students can only register themselves. If register took an address, anyone could register (and name) someone else's wallet. 2. So changing student.score updates the stored data. With memory, the change would be lost. 3. A student with a low score could call register again and reset their score to 0, and anyone could overwrite their own profile freely.

PRACTICE

3.8 PRACTICE — Run the Registry in Remix

  1. Type StudentRegistry into Remix, compile on 0.8.24, deploy on Remix VM with Account A (the owner).
  2. Switch to Account B. Call register("Ada").
  3. In the Remix terminal, click the transaction to expand it. Find the logs section and locate your StudentRegistered event. Which fields do you see?
  4. Call students with Account B's address. Note the returned fields.
  5. Still on Account B, call register("Ada") again. Predict first.
  6. Still on Account B, call updateScore(<Account B address>, 90). Predict first. Read the error: which custom error appeared, and what address is inside it?
  7. Switch to Account A and call updateScore(<Account B address>, 90). Check the ScoreUpdated log shows old score 0 and new score 90.
  8. Call students with Account C's address (never registered). Explain every returned value.
DEBUG

3.9 DEBUG — Registry Bugs

Bug A — doesn't compile

function register(string calldata name) external {
  require(name != "", "Name required");
  students[msg.sender] = Student(name, 0, true);
}
Hint

Which types can Solidity compare with !=? Is string one of them? Section 3.5 shows another way to check for "empty."

Reveal fix

Solidity can't compare strings with !=. Use require(bytes(name).length > 0, "Name required");

Bug B — compiles, but scores never change

function updateScore(address studentAddr, uint256 newScore) external onlyOwner {
  Student memory student = students[studentAddr];
  require(student.enrolled, "Not enrolled");
  student.score = newScore;
}
Hint

Where does student live? Revisit the "copy or reference" simulation in 3.4.

Reveal fix

memory makes a temporary copy, so the stored score never changes. Use Student storage student = ...;

Bug C — compiles, but the front-end never hears about registrations

event StudentRegistered(address indexed student, string name);

function register(string calldata name) external {
  require(bytes(name).length > 0, "Name required");
  students[msg.sender] = Student({name: name, score: 0, enrolled: true});
}
Hint

Declaring an event is like printing a notice. What's the second step to actually put it on the board?

Reveal fix

The event is declared but never emitted. Add emit StudentRegistered(msg.sender, name); after the state change.

CHECK

3.10 CHECK — Knowledge Check

  1. What does a mapping return for a key that was never set?
  2. Why use calldata instead of memory for a string parameter you only read?
  3. How do you check that a string is empty?
  4. Can a contract read its own past events?
  5. Why isn't the name in StudentRegistered indexed?
Reveal

1. The value type's default (0, false, address(0), "", or a struct full of defaults). 2. It avoids copying the data into memory, which saves gas. It's also read-only, which prevents accidental changes. 3. bytes(str).length == 0 4. No. Events live in transaction logs, which contracts can't access. 5. An indexed string is stored as a hash, so apps couldn't read the actual name from the log.

MINI TEST

3.11 MINI TEST — Lesson 3 (pass: 4/5)

Q1. Can you loop over every key in mapping(address => Student)? Why or why not?
Q2. A transaction emits StudentRegistered, then hits a failing require two lines later. Is the event visible on Etherscan?
Q3. Which data location would you use for each? (a) a local variable you'll use to modify a student's stored score (b) a string parameter to an external function you only read (c) a temporary struct you build inside a function and return
Q4. What's wrong with this? function rename(string calldata newName) external { newName = "Anonymous"; students[msg.sender].name = newName; }
Q5. Without the enrolled field, how could the contract tell apart "never registered" and "registered with score 0"?
Reveal answers

1. No. Mappings don't track which keys have been set. To list students, you'd also keep an array of addresses (or rely on events off-chain). 2. No. A revert undoes everything in the transaction, including logs. 3. (a) storage (b) calldata (c) memory 4. calldata is read-only, so assigning to newName is a compile error. If you need to modify a parameter, use memory. 5. It couldn't reliably — a never-registered student also has name "", score 0. You need an explicit marker (like enrolled), or you'd have to rely on the name being non-empty, which only works because register rejects empty names.

BOSS

MISSION 03 — BOSS FIGHT: Decentralized Student Registry

Extend the registry into your own version. Don't just retype 3.7 — add the new features below yourself.

Requirements:

  • A Student struct with at least name, score and enrollment fields.
  • A mapping from address to Student.
  • register takes the name as calldata, rejects empty and over-long names, and rejects double registration.
  • Only the owner can update scores (modifier, with require or a custom error).
  • New: a deregister function that lets a student remove themselves, and emits an event.
  • New: a view function returning a student's name and score.
  • At least two events, each with an indexed address.

Boss test (Remix VM, screenshot each):

  • Student registers with a valid name → succeeds, event in logs
  • Student registers with "" → reverts
  • Student registers twice → second call reverts
  • Non-owner updates a score → reverts
  • Owner updates an enrolled student's score → succeeds, event shows old and new score
  • Owner updates an unregistered address → reverts
  • Student deregisters → enrolled becomes false, event emitted
Design question to answer in writing: After deregister, should the student be allowed to register again? Should their old score be kept? Explain your choice.
