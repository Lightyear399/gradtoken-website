A real finding, disclosed on purpose

The empty-pool sniping vulnerability

Penetration testing surfaced a genuine issue in an early version of GradStaking: because staking rewards split by share of the pool rather than absolute stake size, whoever was the sole staker at a given instant could capture the full reward emission for that instant β€” regardless of how small their stake was. A measured proof-of-concept showed an attacker staking as little as 1 wei could harvest real reward budget for functionally zero capital at risk.

This was not a fund-draining bug β€” no user's principal was ever at risk, and total payouts could never exceed the funded reward budget β€” but it would have quietly siphoned reward budget away from genuinely committed stakers. The fix, live in the deployed contracts linked above, requires both a minimum stake amount and a minimum hold duration before rewards become claimable, while leaving an instant, reward-forfeiting emergency withdrawal always available so user funds are never trapped.

This is included here deliberately. A security page that only lists intentions is a promise; a documented, specific vulnerability that was actually caught and closed before deployment is evidence of a real process.

How this website itself is hardened

Contract security and website security are different problems. This site has no login, no forms, no backend, and no database β€” which already rules out entire categories of attack (SQL injection, auth bypass, server compromise) that simply don't apply to a static page. Beyond that baseline, deliberate choices were made:

  • Zero third-party network requests. Fonts are self-hosted rather than pulled from Google's CDN β€” this site never causes a visitor's browser to contact any domain except the one serving the page itself.
  • Strict Content-Security-Policy. Scripts, styles, and fonts are all restricted to same-origin only β€” no inline scripts, no external script sources, no framing by other sites.
  • No inline event handlers. All JavaScript lives in one external, readable file β€” nothing hidden in onclick attributes or injected at runtime.
  • External links are sandboxed. Every link that opens in a new tab (like the Etherscan links above) uses rel="noopener noreferrer", closing off a known tab-hijacking vector and avoiding leaking this site's URL as a referrer.
  • Security response headers (HSTS, X-Content-Type-Options, X-Frame-Options, and a restrictive Permissions-Policy) are configured at the hosting layer, enforced on every response, not just embedded in the page.
  • A real disclosure channel exists at /.well-known/security.txt, so a researcher who finds something has somewhere legitimate to report it.

Worth being precise about what this does and doesn't mean: no software claim is ever "perfect." This is the honest ceiling for what a static informational site can control β€” it removes every attack surface that's removable. It is a different, smaller claim than the smart contract security above, which carries real financial stakes and is treated with correspondingly more rigor (testing, static analysis, and an audit still to come before mainnet).

Path to mainnet

A professional third-party smart contract audit is scheduled for Phase 2, before any mainnet deployment β€” treated as non-negotiable regardless of how clean internal testing looks. Self-taught and audited is a normal, credible path for a project at this stage; self-taught and unaudited is where user trust breaks. The audit is deliberately sequenced after testnet traction is established, so it can be funded by demonstrated progress rather than a whitepaper alone.
