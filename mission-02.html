Mission 02 — Protect and Fund the Vault

Lesson 2: Functions, Visibility, Modifiers, Access Control & Payable ETH

Dependency: Lesson 1: contract structure, state variables, data types, constructor preview.

  • write functions with parameters and return values, using view and pure correctly
  • choose the right visibility for every function
  • control access using msg.sender, require, modifiers and custom errors
  • accept ETH with payable and msg.value
  • send ETH safely using call and the Checks-Effects-Interactions pattern
THEORY

2.1 THEORY — Functions

function setNumber(uint256 newNumber) public {
  number = newNumber;
}

function → name → parameters → visibility → body (state change)

  • function setNumber(...) — declares a function.
  • uint256 newNumber — a parameter: temporary input.
  • public — visibility: who may call it.
  • number = newNumber; — the state change. This is the only line whose effect outlives the transaction.

Returning values: view and pure

uint256 public number;

// view: reads state, does not change it
function getDouble() public view returns (uint256) {
  return number * 2;
}

// pure: doesn't read or change state at all
function add(uint256 a, uint256 b) public pure returns (uint256) {
  return a + b;
}
KindReads state?Changes state?Costs gas when called from outside?
(none)yesyesyes — it's a transaction
viewyesnono, when called directly as a read
purenonono, when called directly as a read

In Remix, state-changing functions show as orange buttons (transactions); view/pure show as blue (free reads).

ANALOGY

2.2 ANALOGY — The Bank Branch

A bank has:

  • public information anyone can ask for (opening hours) → view functions
  • customer operations anyone with an account can do (deposit) → public / external functions
  • manager-only operations (changing the vault code) → functions guarded by onlyOwner
  • a security guard at each door checking badges → modifiers and require
  • a cash drawer that only opens for deposits at the counter → payable functions

Keep this picture in mind for the whole mission.

THEORY

2.3 THEORY — Visibility

KeywordWho can call it
publicAnyone from outside, and other functions inside this contract
externalOnly from outside (wallets, other contracts). Inside the contract you'd have to use this.f(), which makes a real external call and costs more gas — so normally you don't
internalThis contract and contracts that inherit from it
privateOnly this exact contract
Beginner trap: private and internal only restrict which Solidity code can call the function. They don't hide the function or its logic. The bytecode is public, and verified source code (Mission 04) is readable by everyone.

Rule of thumb: give every function the most restrictive visibility that still works.

THEORY

2.4 THEORY — msg.sender and require

Every call carries the identity of whoever made it: msg.sender.

  • Alice calls the contract → msg.sender == Alice
  • Bob calls the contract → msg.sender == Bob
  • Alice calls Contract A, which calls Contract B → inside B, msg.sender == Contract A

require(condition, "message") checks a condition. If it's false, the whole transaction reverts: every state change in that transaction is undone, and the message is returned to the caller.

Don't use tx.origin (the original wallet that started the transaction) for access control. A malicious contract can trick an owner into calling it and then act on their behalf. Use msg.sender.
require(msg.sender == owner, "Not owner");

INTERACTIVE — Door guard simulation. Alice deployed the contract, so she is owner. Trace each scenario:

Bob doesn't become owner, the contract doesn't disappear, and nothing he attempted is saved.

EXAMPLE

2.5 EXAMPLE — Modifiers

Repeating the same require in every function is error-prone — forget it once and you have a real vulnerability. A modifier names the check once and reuses it.

modifier onlyOwner() {
  require(msg.sender == owner, "Not owner");
  _;
}

function setValue(uint256 newValue) public onlyOwner {
  value = newValue;
}

What _; means: "run the function body here." Code before _; runs first (the guard). Code after _; runs after the body.

INTERACTIVE — Modifier order prediction

uint256 public x;

modifier addOne() {
  x += 1;
  _;
  x += 10;
}

function double() public addOne {
  x = x * 2;
}

Starting from x = 0, what is x after one call to double()?

Reveal

12. Before _;: x = 1. Body: x = 2. After _;: x = 12.

THEORY + EXAMPLE

2.6 THEORY + EXAMPLE — Constructors (formal)

You previewed this in Mission 01. The full rules:

  • A constructor runs once, during deployment, and never again.
  • It can take parameters: constructor(uint256 startValue) { value = startValue; } — you then enter them in Remix next to the Deploy button.
  • It's the standard place to set owner = msg.sender.

Why it matters for security: if you set owner in a normal public function instead, anyone could call it and take ownership. Constructor parameters also matter during verification (Mission 04).

THEORY + EXAMPLE

2.7 THEORY + EXAMPLE — Custom Errors

require with a string message works, but the string is stored in the bytecode and returned on every failure. Custom errors are cheaper and can carry data:

error Unauthorized(address caller);
error AmountTooLow();

modifier onlyOwner() {
  if (msg.sender != owner) revert Unauthorized(msg.sender);
  _;
}
  • error Name(...) declares the error.
  • revert Name(...) triggers it, reverting the transaction like require.
  • Note the logic is flipped: require(ok) versus if (!ok) revert ....
On 0.8.24 use the if (...) revert Error(); form. The shorter require(condition, Error()) form only exists in later compiler versions, so it won't compile with the course compiler.

Both styles are correct. Your final project must use either payable ETH handling or custom errors — many students use both.

THEORY

2.8 THEORY — Handling ETH: payable, msg.value, and Safe Withdrawals

  • A function can only receive ETH if it's marked payable. Sending ETH to a non-payable function reverts.
  • msg.value is the amount of ETH sent with the call, in wei. 1 ETH = 10^18 wei = 1,000,000,000,000,000,000 wei.
  • address(this).balance is the total ETH the contract currently holds.

Mapping preview — the vault below needs to remember a balance per user. That needs a mapping, which Mission 03 covers fully. For now, read this line as "a lookup table from address to number, where every address starts at 0":

mapping(address => uint256) public balances;

EXAMPLE — SecureVault

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract SecureVault {
  address public owner;
  uint256 public value;
  mapping(address => uint256) public balances;

  constructor() {
    owner = msg.sender;
  }

  modifier onlyOwner() {
    require(msg.sender == owner, "Not owner");
    _;
  }

  function setValue(uint256 newValue) public onlyOwner {
    value = newValue;
  }

  function deposit() public payable {
    require(msg.value > 0, "Must deposit ETH");
    balances[msg.sender] += msg.value;
  }

  function withdraw(uint256 amount) public {
    // 1. CHECKS
    require(balances[msg.sender] >= amount, "Insufficient balance");

    // 2. EFFECTS — update state BEFORE sending ETH
    balances[msg.sender] -= amount;

    // 3. INTERACTIONS — external call last
    (bool success, ) = payable(msg.sender).call{value: amount}("");
    require(success, "ETH transfer failed");
  }
}

Why this order? Checks → Effects → Interactions. Sending ETH hands control to the receiver. If the receiver is a contract, its code runs during your withdraw. If you hadn't reduced the balance yet, that code could call withdraw again and again, each time passing the balance check — this is a reentrancy attack, one of the most famous bugs in Ethereum history.

Updating the balance first means a second call sees the already-reduced balance and fails the check.

Why .call{value: amount}("")? .transfer() and .send() forward a fixed 2,300 gas. That's too little for many smart contract wallets, and gas costs of EVM operations have changed in past network upgrades. .call forwards enough gas and returns a success flag, which you must check with require(success, ...). Because .call hands over more gas, following Checks-Effects-Interactions is essential.

Receiving plain ETH — if someone sends ETH to the contract address without calling any function, it reverts unless the contract has a receive function:

receive() external payable {
  // runs when ETH is sent with no function call
}

SecureVault deliberately has none, so ETH can only come in through deposit(), which records who sent it.

PRACTICE

2.9 PRACTICE — Multi-Account Testing in Remix

  1. In Deploy & Run Transactions, set Environment to Remix VM. Select Account A in the Account dropdown. Click Deploy.
  2. Expand the deployed instance (bottom of the panel). Don't click Deploy again — that creates a new contract.
  3. Switch the Account dropdown to Account B. Call setValue(99). Observe the red error: reverted with "Not owner".
  4. Switch back to Account A. Call setValue(42). Observe success, then click value to confirm it's 42.
  5. Still on Account A: in the Value field above the Deploy button, enter 1 and select Ether. Click deposit. Clear the Value field back to 0.
  6. Call balances with Account A's address (copy it with the copy icon next to the dropdown). Predict the number first, in wei.
  7. Call withdraw with 1000000000000000000. Check Account A's ETH balance in the dropdown went back up (minus gas).
  8. Try withdraw again with the same amount. Predict what happens before clicking.
DEBUG

2.10 DEBUG — Three Bugs at the Door

Bug A — this one compiles

modifier onlyOwner() {
  require(msg.sender = owner, "Not owner");
  _;
}
Hint

How many = signs do you need to compare two values?

Reveal fix

= is assignment; == is comparison. msg.sender can't be assigned to, so this doesn't compile. Fix: require(msg.sender == owner, "Not owner");

Bug B — this one also compiles

function setOwner(address newOwner) public {
  owner = newOwner;
}
Hint

Imagine you're Bob, a stranger. What can you do with this function?

Reveal fix

There's no access control, so anyone can make themselves owner and then call every onlyOwner function. Add onlyOwner. Also consider rejecting address(0) as a new owner: require(newOwner != address(0), "Zero address");

Bug C

function withdraw(uint256 amount) public {
  require(balances[msg.sender] >= amount, "Insufficient balance");
  (bool success, ) = payable(msg.sender).call{value: amount}("");
  require(success, "ETH transfer failed");
  balances[msg.sender] -= amount;
}
Hint

Compare the order of the three steps to the SecureVault example. When does the receiver's code get to run?

Reveal fix

The balance is reduced after sending ETH. A malicious receiving contract can re-enter withdraw before the balance is updated and drain the vault. Move balances[msg.sender] -= amount; above the call.

Code reading challenge

function withdrawAll() external onlyOwner {
  (bool success, ) = payable(owner).call{value: address(this).balance}("");
  require(success, "Transfer failed");
}
  1. Who can call it?
  2. Why is onlyOwner there?
  3. What does payable(owner) do?
  4. What happens if a non-owner calls it?
  5. Inside SecureVault, what's wrong with adding this function?
Reveal

1. Only the address in owner. 2. Without it, anyone could take all the ETH. 3. Converts address to address payable so it can receive ETH. 4. It reverts in the modifier before any ETH moves. 5. SecureVault's ETH belongs to depositors, tracked in balances. This function lets the owner take everyone's money while their balances entries still say they're owed it. Access control isn't the only question — you also have to ask whether the rules are fair to users.

CHECK

2.11 CHECK — Knowledge Check

  1. What does msg.sender represent?
  2. What happens if someone sends ETH to a function not marked payable?
  3. What does _; do inside a modifier?
  4. Why prefer .call{value: amount}("") over .transfer(amount)?
  5. What happens to earlier state changes in a transaction that later reverts?
  6. What's the difference between view and pure?
Reveal

1. The address that made the current call. 2. The transaction reverts. 3. Marks where the function body runs. 4. .transfer() forwards only 2,300 gas, which can break smart contract wallets and is fragile against gas-cost changes. .call must be paired with a success check and Checks-Effects-Interactions. 5. They're all rolled back. 6. view can read state but not change it. pure can neither read nor change it.

2.12 MINI TEST — Lesson 2 (pass: 4/5)

Q1. Which visibility lets a function be called from outside and by other functions in the same contract without this.?
Q2. Bob has deposited 2 ETH. He calls withdraw(3 ether) on SecureVault. What happens, and what is his balance afterwards?
Q3. What's wrong with this? function deposit() public { balances[msg.sender] += msg.value; }

Reveal answers

1. public 2. Reverts with "Insufficient balance". Balance stays 2 ETH. 3. It's not payable. Using msg.value in a non-payable public function is a compile error. 4. BOSS

MISSION 02 — BOSS FIGHT: Secure Vault

Build your own vault. Don't copy SecureVault line for line — rename things, restructure it, and make sure you can explain every line.

Requirements:

  • The deployer becomes owner via the constructor.
  • A payable deposit function that rejects zero deposits and tracks per-user balances in a mapping.
  • A withdraw function following Checks-Effects-Interactions and using call{value: amount}("") with a success check.
  • An owner-only function that updates a stored setting, guarded by an onlyOwner modifier.
  • At least one custom error.
  • At least one view function that returns something useful (for example, the caller's balance).

Boss test (run every case in Remix VM and screenshot each):

  • Owner calls the restricted update → succeeds
  • Non-owner calls the restricted update → reverts
  • Account deposits 1 ETH → balance recorded as 100000000000000000
  • Account deposits 0 ETH → reverts
  • Account withdraws 1 ETH → succeeds, balance back to 0
  • Account withdraws more than its balance → reverts

You'll turn these same cases into automated tests in Mission 04.
